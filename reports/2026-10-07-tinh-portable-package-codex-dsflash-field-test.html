Skeptic's verdict

If I wrote PDDs by hand, this saves real time on the part I hate: reading 25 files, mapping 74 template headings, drafting 14,000 words and rendering them. It separated the four version questions better than most juniors would, found genuine contradictions inside the registered PD (the validation-deadline sentence, the Bolivia/Saudi location wording, stale column letters), and never claimed release readiness. The hashes were right this time and it opened workbooks the omp run could not.

But I cannot trust "done" or "PASS" from it. At the inspection checkpoint it told me one of the three ER workbooks was an empty shell. It is the MP1 2022 data, 74,736 tickets. Only my reopening the file caught it. Its page-by-page QA marked all 48 pages PASS, and the final acceptance pass still left a navy table header with black text. The package's gate worked as a prompt. It did not work as a check. The time saved has to be spent on a human spot-check of source claims and rendered pages, and the package gives no way to know where to look.

New findings from this run

N1 · defect A stale dimension tag turns a real 74,736-ticket workbook into "an empty shell"

At the stage-2 checkpoint the agent reported (1) ER_spreadsheet (15).xlsx as "an empty shell containing only ticket_id in A1" and said "no ER workbook exists for MP1 2022", then proposed that as a DATA_GAP. The file's sheet XML declares <dimension ref="A1"> but is 125 MB. With ws.reset_dimensions() it has 74,737 rows × 44 columns, and ticket_timestamp runs 2022-01-03 to 2023-01-01. That is the MP1 data the PDD needs.

Why it matters for the tool: the guide's rule is "never skip unreadable evidence without reporting it", but this was a wrongly reported readable source. A reader who trusts the checkpoint ships a PDD that says 2022 results have no workbook. Nothing in the package tells an agent that openpyxl read-only mode trusts the declared dimension. Fix: add one line to the contract's workbook-reading rules, and make the structural checker flag a workbook whose declared extent is far smaller than its XML size.

verify: ws.reset_dimensions(); sum(1 for _ in ws.iter_rows()) → 74,737 rows; max 44 columns

N2 · defect "PASS" on all 48 pages did not catch a plain contrast defect, and the acceptance pass did not either

The vintage table in §4.4 (PDF p33) has header runs with explicit w:color w:val="000000" on a 2B3957 navy fill, roughly 1.8:1 contrast in Word. In my 100 dpi render of the stage-3 build, the header text is dark on navy. The stage-3 report said "header and label cells rendering dark-on-navy" had been fixed; its QA entry for p33 reads "vintage table with header, eight vintages and total". After prompt C, which says to inspect every final page and fix layout defects, the header runs are still 000000. (LibreOffice's render of the final build looks somewhat lighter, so I would have Word open this page before trusting either.)

N3 · defect The run manifest disagrees with itself, and prompt C did not reconcile it

run_manifest.json coverage_summary: 28 rows, 19 SUPPORTED, 2 SUPPORTED_NA, 5 CONFLICT (C3–C7), 2 DATA_GAP (G7, G-DIAG, G8 listed). status_basis (unchanged by prompt C): conflicts C1, C2, C3, C4, C5, C6 and gaps G1, G7, G8, G9, G-DIAG, G-ECO, G4. The final report adds C7, G-SPLIT, G2, G3, G6, G10, G11. The checkpoint had 37 rows, the final PDD 28. A reviewer cannot tell from the records which items are open.

N4 · polish Prompt C's "26 of 28 passed" is a check of the agent's own script, not of the document

The two failures it reported were a hyphen where the source has an en dash and an arbitrary text-length threshold, both faults in its own checker. The checks were presence-of-value tests. None looked at rendering, header contrast or record consistency. That is the checked-versus-reused language the package asks for, used honestly; it just does not test the things that were wrong.

N5 · note Harness behaviour that affects anyone driving the package from another agent

herdr agent prompt --wait can return agent_prompt_stalled after 5 s on a long prompt even though the agent starts working a moment later. Reading the pane while the agent is working fails (agent_not_idle). A background wait was also reaped under system memory pressure. Having the agent push its own completion message through herdr agent prompt avoided all three.

Recommendations for Tinh's package

  1. Make the integrity gate mechanical. Have check_authored_pdd.py recompute source fingerprints and compare them, and flag spreadsheets whose declared extent is far below their XML size (N1, B2).
  2. Make records self-consistent by construction. Derive coverage_summary and the gap list from one table; fail if status_basis cites IDs that the coverage table does not contain (N3, D7).
  3. Add a rendering-contrast check. Flag table header cells whose run colour and fill have contrast below 3:1, and state a minimum QA resolution (N2, P3).
  4. Fix the SETUP commands you tell people to run. Replace soffice --version with the package's own tool-discovery script; make the audit's default output path compatible with --verify (D2, P4).
  5. Say where scratch work goes. Allow a single outputs/<run>/_scratch/ and exclude it from deliverables (P5).

What this run did not do

  • No numerical recomputation of any supplied result; none was done by the agent either.
  • No human opened the DOCX in Word. The p33 contrast finding rests on the DOCX XML and two LibreOffice renders that differ in apparent text colour.
  • I rendered six pages (1, 2, 12, 26, 33, 47) of the stage-3 build and read three of them (1, 26, 33), plus page 33 of the final build. I did not read all 48.
  • Clause-level checks against VM0043 v1.0 and VCS Standard v4.7 were not possible: neither is in the workspace.
  • One project, one machine, one account, one model at medium reasoning effort. A different model or effort level may behave differently.
