Findings

Three blockers, eight defects in the package or guide, six smaller items. Each one is something a staff member would hit.

Blocker Defect Polish

Blockers

B1

The account ceiling is real, and one setup turn spends it

Message 1 consumed the entire Codex allowance. Nothing in the package or the guide sizes the account requirement. Tinh's August email said a free Codex version is fine, which this run contradicts.

225,737 tokens used; You've hit your usage limit ... Oct 21st, 2026 5:19 PM

B2

Two evidence files cannot be read as text, and the package ships no OCR

The registration deed is 7 pages of scan with zero extractable characters, and the Inegol deed is 5 of 6 pages scan-only. requirements-portable.txt lists four packages, none of them OCR. The only route is Poppler page images plus an agent that can see images, yet no document states that image capability is mandatory.

Verified the route works: a 150 dpi render of the deed was legible and yielded project name, VCS ID 3908 and the three parties.

B3

September dropped the bundled Poppler that August shipped

The August package carried tools/poppler/Library/bin/pdftoppm.exe at version 26.07.0. September has no tools/ folder and neither manifest declares one, so the renderer is now an install step. Worse, the agent found the August copy in a different workspace on this machine and nearly adopted it as this workspace's tool.

data/runs/tinh-20260827/ws/.../tools/poppler/ exists; ref/.../PDD_v1/ has no tools directory

Defects

D1

Installing Poppler does not fix the running shell

The winget install reports success and prints a note to restart the shell. Until then both checks still fail, so an agent that installs and immediately re-checks reports failure with the tool present.

Path environment variable modified; restart your shell to use the new value.

D2

The documented soffice --version check hangs and leaves orphan processes

SETUP.md tells the reader to verify LibreOffice by hand. That command returned nothing on this machine and left soffice.exe and soffice.bin running; the agent had to enumerate and force-kill them. The package's own script finds LibreOffice fine without PATH, so the manual check is stricter than the automated one.

Orphans at PIDs 8516 and 8052, killed by the agent

D3

The guide describes an outputs/ folder the package does not ship

Messages 2 and 3 ask for an outputs/<run-name> path, and the guide presents outputs as one of the workspace folders alongside inputs and library. The extracted package has no such directory, so the first run has to invent it.

Top level after extraction: inputs, library, process, scripts, docs, no outputs

D4

inputs/ mixes evidence with non-project material

The guide says the folder must contain only the selected project, then the package ships project evidence beside official_templates/ and pdd_examples/ under the same parent. What counts as one project folder is not defined on first contact.

inputs/fresh_registry/, inputs/official_templates/, inputs/pdd_examples/

D5

Evidence folder names break naive command lines

Names carry spaces, an ampersand and en dashes. Nothing in the package warns about quoting, and a CLI agent that interpolates a path unquoted will fail or, worse, target part of a name.

documents-CO2 UTILIZATION IN CONCRETE - REMOVALS & REDUCTIONS - CarbonCure - Asia #1/

D6

Version markers collide across document types, and the needed template is absent

One evidence set contains template v4.2, "VCS Version 4.2", Standard v4.7 and v4.0, exemption letters citing Standard v4.3, v4.4 and v4.6, and the deed form's own v4.2 and v4.1. The workspace ships only the v4.4 template, while the example project needs v4.2, so the documented example path can only run with a migration the package explicitly warns not to assume.

See the version matrix below

D7

The reading load is unbounded and nobody says so

Reading every selected input means 390 pages and 708,068 characters of text, plus 6,068 formula cells and 51,452 cached cells across three workbooks. That does not fit one session, and the only mitigation the contract offers is a progress file and a resume, which the guide never surfaces. Nothing bounds what may go into inputs/.

Per-file counts below

D8

The requirement surface is nearly three times what staff will expect

The shipped template yields 74 headings and 36 tables. The guide gives no scale indicator, and earlier internal reporting on this package used "36 sections", which is the table count, not the requirement count.

Template v4.4-FINAL2, 299,989 bytes, 74 Heading styles, 36 tables

Polish

P1

Codex CLI needs a flag the guide does not mention

The workspace is not a git repository, and codex exec refuses to run outside one without --skip-git-repo-check. The guide assumes the desktop app, where this does not arise.

--skip-git-repo-check

P2

Sandbox settings cannot be passed to codex exec resume

The resume subcommand has no sandbox flag. It has to go through -c sandbox_mode="...", which cost a failed attempt.

exit 2, unexpected argument '-s' found

P3

A sandbox can block the interpreter the guide tells you to create

Under the stricter sandbox the agent could not execute the venv's base interpreter, concluded the environment was broken, and hand-built a DOCX from raw OOXML through PowerShell instead of using python-docx. The venv was never broken. In fairness, this machine's Codex default is full access, so the strict policy was the tester's choice, but the guide tells staff to expect policy restrictions without naming this mechanism.

Access is denied on ...\Programs\Python\Python314\python.exe; same venv printed PACKAGES OK once lifted

P4

The capability test does not require the package's own tooling

Message 1 asks for a diagnostic document but not for it to be produced with python-docx. A hand-assembled OOXML file satisfies the wording, which is how one run declared the demonstration done while the real toolchain was blocked.

Diagnostic DOCX 2,582 B built by concatenating XML

P5

The official template is shipped twice, in two formats

library/templates/vcs/ holds the DOCX and inputs/official_templates/ holds a legacy DOC plus a converted copy. Same nominal version, two locations, no statement of which is authoritative for a run.

VCS-Project-Description-Template-v4.4-FINAL2.docx and VCS_Project_Description_Template_v4.4.doc

P6

The guide's numbering skips a section and mixes units

Headings run "Getting started", then 2 through 13, so section 1 is missing; the text refers to "pages 5 to 7" and "page 8" while the headings are sections. Small, but it makes cross-references unreliable.

PDD set up guide, 13 numbered sections, references to pages 2 and 8

What this run did not do

  • No PDD was authored. Messages 3 and 4 were not run, so the authoring, rendering and page-inspection stages of the package remain untested by this run.
  • No requirement was marked supported. All 74 requirement rows stay as DATA_GAP pending the reading that authoring requires.
  • No value was recalculated, no workbook opened in office software, no input modified.
  • The 139, 113, 65 and 44 page documents were text-extracted and searched, not read end to end. Locators in this report point at page numbers, and the full reading is still owed.
  • Claude Code and Gemini CLI were available and unused, so their quota behaviour is unknown. The Codex ceiling is measured; the others are not.
