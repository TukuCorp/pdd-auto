Verdict: the workflow survives an unlisted agent — but its integrity gate is only as good as the agent

An agent the guide never mentions (omp / Oh My Pi) self-routed to docs/agents/OTHER_AGENTS.md, passed every shipped check, separated all four version decisions, and produced a source-grounded 38-page draft with an honest REVIEW_REQUIRED status and no REVIEW_READY claim. The contract's acceptance stage then did real work: it recomputed the 25 input fingerprints, found all 25 wrong, and repaired them. What the package cannot do is catch that failure by itself — neither shipped checker compares recorded source hashes to the files, so a less diligent session would have shipped invented digests inside a manifest that reads as clean.

How it was driven

The four messages are the guide's own copy-paste prompts, sent verbatim (setup §14, prompt A §16, prompt B §17, prompt C §18). Paraphrasing them would have discarded the contract under test. Scope decisions the guide expects the operator to make were answered by me on Tung's behalf, and are recorded as such in the run manifest.

  • Me → omp: herdr agent prompt w2M:p2 "<documented message>" — a pane in the same herdr workspace as this session, so the run is watchable live.
  • omp → me (the alert channel): a watcher polls the agent's status and the pane text every 15 s and exits to raise a notification when the agent finishes a turn — the exit is the alert. Every alert is appended to watch/alerts.log together with the agent's own handoff file and the pane tail, and the instance then spawns a detached successor so the channel is never left unarmed. A token-claimed lock keeps exactly one watcher alive, and the agent was asked to overwrite omp/status.md and end each reply with OMP_TURN_END <stage> <verdict>, so every alert carries its own report.
  • One method correction worth recording. The first version of that watcher keyed on the agent's status going working → idle, and it missed a real completion: this agent can answer a prompt and settle back to done without herdr ever reporting working, so the transition it waited for never happened. The detector was rewritten to key on the pane text advancing and then going quiet — with spinner, token counter and prompt bar normalised out first, so a redraw cannot fake a turn end — or on the handoff file changing. Re-tested against that exact case: a prompt answered entirely inside done now raises the alert, confirmed live at 15:50:15.
  • Decisions I made for the operator: confirm scope; pin methodology to VM0043 v1.0 (as registered and cited throughout the evidence) with the library's v1.1 recorded as a conflict rather than applied; authorise DATA_GAPs for absent non-public evidence; and require the run to ignore the existing codex run's narrative so the two runs stay independent.

The hash incident, in full

This is the single most important thing the run produced, because it is the failure mode the package exists to prevent and the package caught it only through the agent's honesty.

The authored run's source_manifest.json recorded a SHA-256 fingerprint for each of the 25 project files. Recomputing them showed 0 of 25 matched. The recorded strings are all valid hex, but every one is 58–62 characters long instead of 64, and each agrees with the true digest for exactly the first 16 hex characters before diverging:

Recorded versus real fingerprints, two examples. A truncation would keep the true prefix; these do not.
FileRecordedLenRealShared prefix
kml_2023_10_25.kml185e690b09862ab3f0b6e53b…60185e690b09862ab38f316b3f…16
(1) ER_spreadsheet (15).xlsxdead5e3ec80e2c07d54b57ec…62dead5e3ec80e2c071ca463d3…16

No hash algorithm reproduces the recorded values — SHA-256, SHA-1, MD5, SHA3-256 and BLAKE2b were all tested against the real file, and only SHA-256 shares a prefix at all, at 16 characters. A 64-bit agreement followed by divergence and a drifting length is the signature of text generated to look like a digest, not a digest of anything. The artifact hashes for PDD.docx and PDD.pdf in the same manifests are correct and verifiable, which is consistent with those being written by a script while the source fingerprints were written as text.

Why it matters for the tool: the package's promise is that a reviewer can trust the run's evidence lineage. check_authored_pdd.py checks DOCX structure against the template; review_records.py checks that coverage rows, version records and visual-QA metadata are internally consistent. Neither one opens a source file. Nothing shipped compares a recorded fingerprint to the file it names, so a fabricated list produces a manifest that reads as clean and a run whose status is REVIEW_REQUIRED for entirely different reasons. The only thing that caught it was prompt C instructing the agent to recompute — and an agent willing to report its own failure. The agent's own root-cause label ("truncated to 60–62 chars") is also wrong for the reason above; the remediation was right, the diagnosis was not.

After the repair, independently re-verified: 25/25 paths resolve, 25/25 digests match the files on disk, all 64 characters, and both artifact hashes match the live DOCX/PDF with visual QA bound to those same hashes.

Findings

Each finding is one rule with its mechanism, and the command or artifact that shows it. Levels are assigned by what a staff member loses: a finished task, an hour, or minutes.

Blocker Defect Polish

Blockers

B1 · Blocker

The supplied results sit in workbooks a session cannot open

The contract requires every reported calculation to be explained with its workbook, sheet and cell lineage — but the two largest evidence files are 192.3 MB (360,903 rows) and 111.0 MB (210,720 rows). The agent's Python kernel died with exit 130 while sampling the larger one, after which it declined that workbook outright as a memory guard and structure-sampled only the smaller. The codex run hit the same wall from the other side, surveying only 6,068 formula and 51,452 cached cells.

Measured dimensions A1:AX210720 and A1:AS360903; agent limitation "183 MB ER workbook unopened (memory guard); 106 MB workbook structure-sampled only" (MiB); kernel exit 130 in the pane transcript. Nothing in the guide bounds what may go into inputs/ or warns that the supplied results may be unreadable at this size.

B2 · Blocker

The integrity gate can be satisfied by invented fingerprints

The package ships no check that compares a recorded source hash to the file it names. check_authored_pdd.py validates DOCX structure; review_records.py validates record consistency; neither opens a source. So a manifest full of fabricated digests reads as clean, and the run's status says REVIEW_REQUIRED for unrelated reasons. This run produced exactly that and it survived every shipped check.

25/25 mismatches on recomputation; recorded lengths 58–62 instead of 64; only prompt C's recompute instruction found it. Fix: make the shipped checker recompute and compare source fingerprints, and require them to be written programmatically.

Defects

D1 · Defect

The structural checker refuses to write its report where you tell it to

check_authored_pdd.py --report rejects an absolute path and then rejects anything outside outputs/, so the tool cannot report into scratch or a reviewer's own folder. The guide's reference-commands section lists the command without ever showing a --report value, so the constraint is discovered by failing.

ValueError: Expected a workspace-relative path, then error: --report must be under outputs/.

D2 · Defect

The documented LibreOffice check is stricter than the automated one, and broken

SETUP tells the reader to verify LibreOffice with soffice --version. That prints nothing on this machine — and on the 21 September run it also left orphan soffice processes that had to be force-killed. The package's own script locates and uses LibreOffice correctly without any PATH entry, so the manual step can only produce a false alarm.

Two independent agents hit this: codex on 21 Sep, omp on 24 Sep (error: command not found: soffice, then successful headless conversion via the absolute path).

D3 · Defect

The guide mandates a virtualenv the setup prompt tells the agent to skip

SETUP creates .venv as a required step; the setup prompt says to check existing installations first and reuse a working local environment. The agent correctly reused the system Python 3.14.2 and never built one — which is fine, except that the pass/fail verdict depends on which interpreter you run the checks with.

Same machine, same package: with the system Python 3.14.2, check_portable_pdd.py is OK; with another interpreter lacking reportlab, the identical command reports PORTABLE CHECK: FAILED. The guide never says which interpreter is authoritative.

D4 · Defect

The example folder the prompts point at is empty

The guide presents inputs/pdd_examples as the optional examples of structure and detail, and prompt A carries it as a field. It ships as a 310-byte README and nothing else, so the structure-only guidance the contract offers as a safety net does not exist.

ls inputs/pdd_examples → README.md only. The agent recorded "inputs/pdd_examples (empty; no examples used)".

D5 · Defect

The official template ships twice, and the two agents picked different ones

One copy is library/templates/vcs/VCS-Project-Description-Template-v4.4-FINAL2.docx; another is a legacy .doc plus a converted copy under inputs/official_templates/. Nothing states which is authoritative for a run, and the divergence is real: codex authored against the legacy .doc, omp against the library .docx.

Both locations confirmed on disk; each run's run_manifest.json names a different template path.

D6 · Defect

The run manifest's fields do not match the table that describes them

The guide's artifact table says run_manifest.json carries the observed agent identity; the shipped validator does not require such a field and this run has no agent or model key at all, recording identity under reviewer and method instead. A reviewer following the table finds nothing to read, and nothing validates the file's schema or encoding — which is how the same file carried both of the residual defects below.

Top-level keys present: artifact_hashes, authority_roles, coverage, gaps, inputs_note, limitations, method, output_folder, project, reviewer, run_name, selected_input, status, status_reasons, template, tools, versions, visual_qa.

D7 · Defect

Gaps can live outside the coverage table, so the validator reports clean

The contract says an unresolved item is a DATA_GAP row and that a gap "is not complete". This run recorded 12 non-blocking gaps in a separate array and marked all 62 coverage rows SUPPORTED or SUPPORTED_NA, so the shipped validator returns no issues while 12 gaps are open. The agent disclosed and justified the choice, and it is a defensible reading — but the package should decide which representation is canonical instead of leaving two that disagree.

Validator returns no issues; coverage_states = {SUPPORTED: 60, SUPPORTED_NA: 2}; gaps = GAP-01…GAP-12.

D8 · Defect

Evidence folder names break naive path handling, and nothing warns about it

Names carry spaces, an ampersand and en dashes. The en dash is the dangerous one: UTF-8 bytes decoded as cp1252 turned the folder name in this run's run_manifest.json into mojibake, so the recorded path did not resolve to any folder on disk. The August package hit the same class of problem from a renamed folder, leaving 26 manifest entries unverifiable.

Recorded codepoints U+00E2 U+20AC U+201C where the folder has U+2013; os.path.exists(selected_input) was False until repaired.

LibreOffice is not on PATH and the guide assumes it is

Every render needs the absolute path C:\Program Files\LibreOffice\program\soffice.exe. The agent found it and moved on, but the guide's setup section presents a bare soffice as the expected command.

P2 · Polish

Two evidence PDFs have malformed cross-reference headers

pypdf reports invalid pdf header and incorrect startxref pointer for two files, then recovers and extracts them. Harmless here, but a stricter reader would treat them as unreadable evidence and a reviewer should know they are not clean.

Two warnings during a 652-page text survey; both files still yielded page counts and text.

P3 · Polish

No minimum resolution is set for page QA, so the QA claim is narrower than it reads

The contract requires inspecting every rendered page at readable resolution but never states a floor. This run rasterised at about 80 dpi (680×880 px). Reading one of those pages myself, the body and table text is legible — but hairline table borders, cell shading, sub/superscripts and en-dash-versus-hyphen distinctions are not resolvable at that scale, so a "38/38 PASS" cannot have covered them.

Page images 680×880 px; independent visual read of qa/page-33.png; the 21 September run used 150 dpi. Recommend stating a minimum (150 dpi) in SETUP.

P4 · Polish

The audit writes into the package it is auditing

Running the documented audit rewrites docs/PORTABILITY_AUDIT.json inside the delivered package and records device-local absolute paths in it. A receiving device therefore mutates the package on first contact, which quietly undermines the "files match the shipped manifest" claim the guide invites you to make.

report=…\PDD_v1\PDD\docs\PORTABILITY_AUDIT.json, regenerated on each run with local paths.

P5 · Polish

Agents leave their scaffolding inside the delivered package

This run left tmp/startup_diag/, an author/ folder with six build scripts plus a __pycache__, and transient LibreOffice lock files inside the run folder. The contract tolerates project-specific formatting code, but there is no instruction to keep scratch out of the package or to clean up, and no artifact list that says which files a run is allowed to leave behind.

tmp/startup_diag/ (docx, pdf, png); outputs/carboncure_omp_demo_01/author/ with part1…part6 scripts.

P6 · Polish

The guide's numbering skips a section and mixes sections with pages

Headings run "Getting started" then 2 through 13, so section 1 is missing, and the prose cross-references "pages 5 to 7" while the headings are sections. Cross-references in a document staff are told to follow step by step become unreliable.

Carried over unchanged from the 21 September run's findings; still present in the 18 September guide.

The package's own checkers, on the final artifacts

  • check_authored_pdd.py → REVIEW_REQUIRED with one finding, and it is template-side: the two "missing" headings are a truncated inter Heading-4 fragment and the appendix x: <title of appendix> placeholder, neither of which exists in the authored PDD. 9,849 editable words, 34 tables, 76 headings, 0 empty leaves, 0 template-text matches, 0 placeholders, 38 pages, 0 missing review records.

What this run did not do

  • No source was recalculated, and none should be. The contract forbids it; the workbooks were opened read-only with keep_links=False and never resaved. No value in this report was recomputed from a formula.
  • The two largest workbooks were never read in full. 571,623 ticket rows and their formula/cache cells remain unaccounted for. Every calculation claim in the authored PDD is corroborated from the monitoring and verification reports rather than from the workbooks themselves.
  • The QA claim is bounded by 80 dpi. Gross layout failures and missing rows are detectable at that scale; hairline borders, shading, sub/superscripts and dash fidelity are not, and no human opened the DOCX in Word.
  • Not a Verra judgement. REVIEW_REQUIRED describes this workflow's own gates. It is not validation, registration or submission acceptance, and the run never claims otherwise.
  • One project, one machine, one account. CarbonCure (VCS 4019) on this device. The Inegol set's scan-only deeds — which need OCR the package does not ship — were not retested here.
  • No cleanup performed. The agent's run folder, its author/ scripts and tmp/startup_diag/ were left in place so the run stays auditable; only my own temporary structural-check report was deleted after use.
